# Передача работы Claude: два аудита Kronos Agent OS

Дата подготовки: 2026-10-04 (Asia/Makassar). Это инструкция для продолжения
работы, а не свидетельство, что production готов. Перед любым действием проверь
актуальные `git status`, `origin/main`, код и сервер: статусы ниже — снимок.

## Цель и правила

Довести до проверяемого завершения [общий реестр](2026-09-08-remediation.md)
локального и production-аудитов. Не заменяй production-проверку локальными
тестами. Следуй корневому `AGENTS.md`: один логический фикс — один атомарный
коммит; сохраняй чужие незакоммиченные изменения; не меняй зависимости,
публичную/приватную конфигурацию и системные права без согласования; не
публикуй секреты, персональные данные и содержимое БД в отчётах.

Не считай исторические таблицы реестра текущим состоянием сервера. Прежде чем
отмечать пункт закрытым, покажи проверку критерия приёмки на актуальном коде
и, для production-пункта, на работающем сервере. Старые неизвестные исходы
внешних операций и legacy-записи памяти нельзя автоматически повторять,
отменять или приписывать пользователю.

## Что осталось — порядок работы

1. **A02, граница данных пользователей — следующий локальный фикс.**
   `kronos/tools/session_search.py` и `SwarmStore.search_sessions()` сейчас
   ищут без доверенного `user_id`; `kronos/memory/knowledge_graph.py` хранит
   entities/relations без user scope, вызовы из `memory/nodes.py` не задают
   его. Проследи источник identity от транспорта до поиска/записи, сделай
   миграцию и отрицательные cross-user tests. Legacy-записи с неизвестным
   владельцем изолируй, не присваивай первому обратившемуся.
2. **F13:** scoped reset должен охватывать raw session search, KG, Mem0,
   локальный FTS, shared facts и отложенные background writes. Докажи, что
   удалённая память не возвращается после гонки с writer.
3. **F08–F10:** operator reconciliation неизвестных эффектов, надёжное
   stop-уведомление, обычные ответы и остальные producers в outbox, ремонт
   доставки; инвентаризация всех внешних эффектов, idempotency и
   fail-closed журналирование. Не делай слепой retry неизвестного исхода.
4. **F12:** durable session budget ledger, атомарные reservations, учёт
   неизвестного billing outcome и тест реального Mem0 adapter. Fake transports
   не заменяют интеграционную проверку.
5. **F14–F15:** согласованность desired/effective Dashboard settings и
   неблокирующий model/memory I/O с latency/responsiveness тестом.
6. **A01/A03/A05/A06:** Discord owner allowlist и безопасные DM/context
   boundaries; полноценное изображение из browser screenshot вместо
   обрезанного base64; keyless FTS/shared retrieval только после A02;
   end-to-end chat→tool→approval→effect→delivery, fault injection и live gate.
7. **Production:** после отдельного согласования устранить `PROD-03` (права
   session/DB и umask), `PROD-04` (runtime/admin separation), `PROD-11`
   (env-source основного агента), контролируемо включить approvals
   (`PROD-05`), проверить полную off-host backup/restore (`PROD-07/A04`),
   all-agent readiness/alerts, ingress/SSH, release identity/rollback,
   реальные Telegram usernames/routing и историческую сверку DB.
   `V01–V03`: актуальный CVE scan с разрешённым источником, план reboot и
   ручная сверка прежних pending approvals/расходов.

## Как работать и передать на проверку Codex

Для каждого пункта сформулируй угрозу/корневую причину, минимальный фикс,
миграцию старых данных (если нужна), негативные тесты и критерий приёмки.
После каждого логического изменения делай отдельный commit; перед push/deploy
покажи clean status, diff, результаты тестов, dry-run и rollback. Не
используй `git reset --hard` или удаление production state. Включение
защитных флагов, изменение unit/env/прав и любые сетевые правила согласуй
отдельно; не считай кодовый gate работающим при выключенном effective flag.

Когда закончишь этап, передай Роману текст, который можно вставить в эту
задачу Codex для независимого ревью. Формат:

1. Пункт реестра, что исправлено и что намеренно не исправлено.
2. Ветка, точный HEAD SHA, список атомарных коммитов и `git status`.
3. Список изменённых файлов и краткое описание каждого; ссылка на PR/дифф,
   если есть. Не присылай секреты или дампы пользовательских данных.
4. Точные команды тестов и результаты, включая миграцию на копии старой
   схемы, cross-user/fault-injection случаи и пропущенные проверки с причиной.
5. Production: какие изменения реально развёрнуты, время, effective config
   **без значений секретов**, версии файлов/manifest, health и проверка
   поведения. Если не развёрнуто — напиши «не развёрнуто».
6. Риски, сценарий отката без потери состояния, неизвестные исходы, решения,
   требующие согласования, и следующий пункт.

Попроси Codex провести review **до** закрытия пункта: проверить дифф,
безопасность/изоляцию данных, миграцию, тесты и production evidence. Не
формулируй «всё исправлено» по одному зелёному pytest или health endpoint.
